## 무엇을 비교했나

두 예측기는 **같은 함수**(`parse/approval_layers.py`)와 **같은 규칙·명부**(케이스마다 참고 문서만으로 귀납)를 쓴다.
다른 건 하나 — 층을 **코드가 순서대로** 부르나(layered), **모델이 골라서** 부르나(agent).

| 도구 (= layered 층) | 하는 일 |
|---|---|
| `classify_doc(title, body)` | 업무항목·금액 |
| `lookup_delegation(work_type, amount)` | 최종 결재 직위 (priority 첫 매칭 → 폴백) |
| `route_team(title, body)` | 담당 팀장 (키워드 점수, 동점 여부) |
| `lookup_cooperation(work_type, title, body)` | 협조 직위 |
| `lookup_roster(title)` | 그 직위의 이름 후보 |
| `search_past(query, k)` | 비슷한 과거 문서의 결재선 |

에이전트 시스템 프롬프트는 도구 설명 + "후보 밖 이름 금지" + 출력 형식뿐이다. 순서는 지시하지 않았다.
최대 호출 8회.

## qwen3:8b 의 tool calling 은 안정적이었나

**형식은 안정적이다.** 12케이스 모두 올바른 도구 이름·인자로 불렀고, 호출 초과·JSON 누락·인자 오류가 0이다.
문제는 **계획**이다. 항상 3~4회 만에 멈추고 결재선을 낸다 — 기안·검토 칸의 뼈대를 줄 유일한 도구
(`search_past`)를 한 번도 부르지 않았다. layered 에서 기안·검토는 "남는 칸 vote"(과거 결재선 다수결)가
채우는데, 에이전트는 그 층에 닿지 않으니 **결재 칸 + 협조 조회 결과만으로** 결재선을 만든다.

요청서 5번("안정적으로 못 하면 멈춤")에는 해당하지 않아 끝까지 쟀다. 모델을 바꿔 볼 가치는 있다
(아래 "다음").

## 판정

**layered 가 모든 지표에서 이긴다** — 직위 2.2배, 이름 6배, 칸 수 1.9배, 300배 빠르고, 후보 밖 이름이 구조상 0.
에이전트가 이긴 칸은 없다. 차이의 대부분은 "어떤 도구를 부를지"와 "결과를 어느 칸에 넣을지"를
모델에 맡긴 데서 나왔다 — 둘 다 결재선 문제에서는 **답이 정해진 절차**다.
