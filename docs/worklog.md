■ 과제 3: T4 관보 OCR 트랙 세로 관통 (collect → parse → evaluate → CER 숫자)
무엇을 했는지:
  - collect/local_files.py — `TextLayerCollector`. DATA_ROOT/t4/*.pdf 를 순회하고
    정답을 같은 PDF의 텍스트 레이어(pymupdf `get_text`)에서 뽑는다.
    즉 이 트랙이 재는 건 "텍스트 레이어 vs OCR" 이지 OCR 절대 정확도가 아니다.
  - parse/render.py — 페이지별 200dpi PNG를 DATA_ROOT/t4/rendered/<pdf명>/p{n}.png 에
    저장, 있으면 재사용.
  - parse/ocr_apple.py — ocrmac(Apple Vision), 인식 언어 ko-KR + en-US.
  - evaluate/text_cer.py — jiwer CER/WER. 정규화(NFC + 공백 압축 + strip)를
    `normalize()` 로 분리하고 정규화 전(`*_raw`)/후를 둘 다 계산.
  - tracks/t4_gazette_ocr.py — 페이지별 점수 + 문서 전체 + 전체 평균을
    results/t4/<YYYYMMDD-HHMM>.json 에 저장. 본문 텍스트는 저장하지 않는다.
  - cli.py — `wat run t4 [--pages N] [--docs N] [--dpi N]`.

막힌 지점:
  1. DATA_ROOT/t4 에 **진짜 관보 PDF가 없다.** 있는 건 이전에 만든
     smoketest-synthetic.pdf 1장(1페이지, 합성 대통령령 텍스트)뿐이다.
  2. 합성 PDF는 벡터 텍스트를 그대로 렌더링한 거라 OCR 난이도가 실제 관보 스캔본과
     다르다. 여기서 나온 CER은 파이프라인 점검 숫자이지 벤치마크 결과가 아니다.
  3. 결과 파일명이 분 단위(YYYYMMDD-HHMM)라 같은 분에 두 번 돌리면 앞 결과를 덮었다.

해결:
  1·2 → 데이터는 만들지 않고 그대로 두고, 합성 PDF로 파이프라인만 세로로 관통시켰다.
     페이지 수 제한(--pages)·dpi 변경 재렌더링 같이 1페이지 PDF로 확인 못 하는 경로는
     스크래치패드에 임시 WAT_DATA_ROOT 를 잡고 5페이지 픽스처로 따로 검증했다.
  3 → 같은 분에 충돌하면 초까지 붙인 파일명으로 떨어뜨린다.

결과 (합성 PDF 1장, 파이프라인 점검용 숫자):
  CER 0.0551 / WER 0.3452 (정규화 후), CER 0.0606 / WER 0.4225 (정규화 전), 0.92s
  WER이 CER 대비 크게 높은 건 Vision이 단어 안에 공백을 끼워 넣기 때문
  ("제34567호" → "제3 4 5 6 7 호"). 한국어에서는 어절 단위 WER보다 CER을 본다.

다음 단계:
  - 진짜 관보 PDF를 DATA_ROOT/t4 에 배치하고 다시 측정 (이게 실제 T4 숫자)
  - 정답을 국가법령정보 공개 텍스트로 바꾼 비교(collect/local_dir.py 경로)와 대조

■ 과제 4: T4 관보 OCR 첫 실측 (제21317호) — CER 숫자 확보
무엇을 했는지:
  - DATA_ROOT/t4 에 관보 PDF 3개 도착 확인. 페이지 수 검증 결과 801/440/337 전부 일치.
    세 파일 모두 텍스트 레이어가 살아 있다(앞 5p 기준 700~5,600자/페이지).
  - smoketest-synthetic.* / _render/ / rendered/smoketest* 정리 완료.
  - `--only` 옵션 추가. 파일명 정렬상 801페이지짜리(제21315호)가 첫 번째라
    `--docs 1` 로는 "오늘 건드리지 말 것"에 걸린다. 대상을 파일명으로 지정하도록 했다.
  - 제21317호 앞 3페이지 → 앞 20페이지 순으로 실행.

측정 결과 (제21317호, 200dpi, Apple Vision):
  20페이지 전체 평균 CER 0.4367 / WER 0.5343, 29.9초 (페이지당 약 1.5초)
  results/t4/20260908-1532.json

막힌 지점: CER이 0.44로 비상식적으로 높고, CER > WER 이라는 이상한 형태가 나왔다.
해결 (원인 두 개로 갈림 — 둘 다 OCR 품질이 아니라 측정 아티팩트):
  1. 목차 페이지(p1~3)의 점선 리더.
     텍스트 레이어 글자의 48~64%가 점선 리더(`·`)다. 목차 줄이
     "법률제21882호(국회법 일부개정법률) ·········· 4" 형태라 점이 본문보다 많다.
     OCR은 점선을 재현하지 않으므로 CER이 그대로 점선 비율을 따라간다.
     점선을 빼고 재면 CER 0.676→0.178, 0.621→0.088, 0.503→0.084 로 정상화된다.
  2. 본문 페이지(p4~20)의 2단 조판 읽는 순서.
     글자 다중집합 겹침이 0.91~0.99인데 CER은 0.16~0.49다. 글자는 맞게 읽었고
     순서가 다르다는 뜻. 블록 x좌표군이 [50, 300](페이지폭 595)으로 2단 조판이다.
     parse/ocr_apple.py 가 Vision 관측을 y→x 단순 정렬해 두 단을 지그재그로 섞고 있다.
  3. 해상도는 원인이 아님을 확인. 200/300/400/600dpi 에서 CER 0.676→0.678 로 무변화.
     즉 글자가 작아서 못 읽는 게 아니다.

결과 해석: 0.4367 은 OCR 정확도가 아니다. 단 정렬을 고치기 전까지 모델 비교에 쓸 수 없다.
  참고로 CER은 글자 오류율((틀린+빠진+끼어든 글자)/정답 글자 수)이고, 한국어는
  띄어쓰기 변동 때문에 단어 단위(WER)가 과대평가되어 글자 단위가 표준이다.
  정답은 관보 PDF 텍스트 레이어. 목적은 OCR/VLM 후보별 한국어 공문서 인식 정확도를
  직접 측정해, 결재문서 이관 시 텍스트 레이어/OCR/VLM 선택 근거를 확보하는 것.

다음 단계:
  1. parse/ocr_apple.py 에 단(column) 인식 정렬 추가 후 재측정. 이게 진짜 T4 숫자.
  2. 점선 리더를 정규화에서 어떻게 다룰지 결정(제거 vs 유지). 제거하면 목차 페이지가
     의미 있어지지만, 지표를 결과에 유리하게 손보는 것이므로 명시적으로 기록하고 간다.
  3. 그 다음에야 OCR/VLM 후보 비교(상용 API 비교군 소량)로 넘어간다.
  4. 제21315호(801p)·제21316호(440p)는 아직 미실행.

■ 과제 5: T4 CER 아티팩트 제거 — 0.4367 → 0.1017
무엇을 했는지: 앞선 측정의 CER 0.4367 이 OCR 품질이 아니라는 의심을 확인하고,
  원인을 하나씩 분리해 걷어낸 뒤 재측정했다.

막힌 지점 / 해결 (가설이 틀린 것도 그대로 남긴다):
  1. [가설 실패] "2단 조판 때문에 읽는 순서가 섞인다"
     → 세로 여백 탐지 + 단 인식 정렬(XY-cut)을 구현했으나 CER 0.4367 → 0.4429 로 악화.
       실제 본문 페이지를 열어보니 1단이었다. pymupdf 블록의 x≈300은 가운데 정렬된
       제목·서명 줄이었고 내가 2단으로 오독했다. 코드는 되돌렸다.
  2. [가설 실패] "글자가 작아 200dpi에서 못 읽는다"
     → 200/300/400/600dpi 에서 CER 0.676 → 0.678. 해상도는 무관하다.
  3. [진짜 원인 A] 정답을 pymupdf 기본 블록 순서로 읽고 있었다.
     그건 PDF에 그려진 순서지 사람이 읽는 순서가 아니다. OCR은 화면에 보이는 순서로
     읽으므로, 글자를 다 맞혀도 순서 차이가 CER로 잡혔다.
     → get_text(sort=True) 로 시각적 읽는 순서 사용. CER 0.2755 → 0.1105. 20페이지 전부 개선.
  4. [진짜 원인 B] 표기 관습 차이. 오류 문자 빈도를 집계해 찾았다.
     - 목차 점선 리더: 정답 글자의 48~64%가 점. 점 3개 이상 연속을 리더로 보고 제거.
     - 따옴표: 정답 둥근 따옴표 vs OCR 곧은 따옴표.
     - 가운뎃점: 정답은 ᆞ(U+119E, 아래아), OCR은 •(U+2022). 앞서 쓴 점 필터에 이 문자가 없었다.
     - 공백: 관보는 자간을 공백으로 벌린다("대 통 령"). 정답 글자의 25~30%가 공백.
       공백 제외 CER 을 별도 지표로 병기.

결과 (제21317호 앞 20페이지, 200dpi, Apple Vision):
  CER 0.1017 / 공백 제외 CER 0.0797 / WER 0.3491 / 정규화 전 CER 0.4324
  페이지별 CER 0.060 ~ 0.168, 29.2초(페이지당 약 1.5초)
  results/t4/20260908-1601.json

남겨둔 것: 목차 글머리표 ○ 를 · 로 읽는 오인식 96건. 이건 진짜 OCR 오류라
  정규화하지 않았다. 지표를 결과에 유리하게 손보면 모델 비교의 근거가 사라진다.

다음 단계:
  1. 같은 페이지·같은 정규화로 다른 OCR/VLM 후보 측정 → 나란히 비교(이게 원래 목적).
  2. 제21315호(801p)·제21316호(440p) 전체 측정으로 표본 확대.
  3. 정답이 텍스트 레이어인 구도의 한계는 그대로다. 스캔본은 국가법령정보 공개 텍스트를
     정답으로 붙이는 경로(collect/local_dir.py)에서 다룬다.

■ 과제 6: T4 측정 신뢰도 다듬기 — 지표 분리·페이지 유형·표본 설계
무엇을 했는지:
  - evaluate/text_cer.py: 리더 제거를 **기본 정규화에서 뺐다.** cer(리더 포함) /
    cer_no_leader(리더 제거)를 둘 다 기록한다. 지표를 유리하게 만드는 조작이
    기본값에 숨으면 모델 비교의 근거가 사라지기 때문이다.
  - char_overlap(글자 다중집합 겹침) 정식 지표 추가. 순서를 무시하고 "글자를 맞혔는지"만 본다.
    T1의 필드 추출처럼 읽는 순서가 성능과 무관한 과제에 CER보다 가깝다.
  - collect/page_type.py: 텍스트 레이어 통계로 toc / table / body_2col / body_1col 분류.
    규칙 4개, 순서대로 처음 걸리는 것. 결과 JSON 페이지별 항목과 요약에 유형별 평균 추가.
  - 표본 설계: --select mixed. 전체 페이지를 유형으로 분류한 뒤 유형을 돌아가며 한 장씩 집는다.
    앞 20장만 보면 목차·공포문에 치우쳐 문서를 대표하지 못한다.
    고른 방식은 결과 JSON의 page_selection 에 그대로 기록한다.

막힌 지점: "cer / cer_no_leader 둘 다 기록, 기본값은 바꾸지 마"는 지시가 현재 코드와 충돌했다.
  기본 정규화에 이미 리더 제거가 들어 있어서, 그대로 두면 두 값이 항상 같아진다.
해결: 리더 제거를 기본에서 옵션으로 뺐다. cer 은 올라가고 cer_no_leader 가 기존 값을 잇는다.
  헤드라인 지표를 몰래 바꾸지 않는다는 원칙에도 이쪽이 맞다.

결과 (200dpi, Apple Vision, 유형 섞어 20페이지씩):
  제21317호(337p): CER 0.4169 / 리더제외 0.2277 / 겹침 0.5933
  제21316호(440p): CER 0.3493 / 리더제외 0.1359 / 겹침 0.6922

  유형별로 갈라 보면 그림이 완전히 달라진다.
    body_1col : 0.1193 (겹침 0.984) / 0.1528 (0.994)  ← 로컬 OCR이 안정적으로 읽는다
    table     : 0.3941 (겹침 0.663) / 0.1460 (0.968)  ← 문서마다 갈린다
    toc       : 리더 제외 시 0.0832 / 0.0849          ← 리더가 전부였다

  표에서 겹침이 0.66까지 떨어지는 건 순서가 아니라 글자를 아예 못 읽었다는 뜻이다
  (21317 p228은 겹침 0.295). 로컬 OCR이 무너지는 지점이 표라는 건,
  이관 PDF에서 표·서식 첨부를 따로 다뤄야 한다는 신호다.

다음 단계: 같은 페이지·같은 정규화로 두 번째 OCR 후보 측정 → 나란히 비교.

■ 과제 7: T1 결재문서 트랙 — T1a 필드 추출 + T1b 결재선 (gold 직접 제작)
무엇을 했는지:
  - 진단: PDF 10건 텍스트 레이어·결재란 위치 확인. metadata.tsv 스키마 확인.
    `결재정보` 컬럼은 10건 전부 "(화면에 표시 항목 없음)" → 포털에 결재선 없음이 데이터로 확인.
  - collect/opengokr_local.py: metadata.tsv → ground_truth. 컬럼명 헤더 그대로.
  - parse/fields_textlayer.py: 텍스트 레이어 + 블록 좌표로 T1a 6필드 규칙 추출.
  - parse/region_crop.py: 결재란 영역 자동 판별(상단 격자형 vs 하단 시행문형) + crop.
  - parse/approval_ocr.py: 같은 함수가 OCR(ocrmac)과 텍스트 레이어 둘 다 처리.
    직위 위 / 이름 아래 배치를 좌표로 짝지어 칸을 만든다.
  - evaluate/field_match.py, evaluate/approval_match.py.
  - approval_gold.tsv 직접 제작: 10문서 56행, 실칸 49, 이름 미판독 1.
    PDF 결재란을 눈으로 보고 만들었다. 리포 밖(DATA_ROOT)에만 둔다.

막힌 지점: 결재란을 페이지 **상단**에서만 찾아 8/10 문서에서 못 찾았고,
  "결재란이 이미지라 OCR 경로가 기본이어야 한다"고 결론 낼 뻔했다.
해결: 전체 페이지를 렌더링해 눈으로 확인하니 결재란 대부분이 **하단 시행문 블록**에 있었다.
  영역을 고치고 다시 재니 **10건 모두 결재란이 텍스트 레이어로 존재**했다.

■ 과제 8: T1b 칸 짝짓기 보정 + 두 번째 OCR 후보(PaddleOCR) 비교
무엇을 했는지:

막힌 지점 / 해결:
  1. 이름 짝짓기가 "직위 아래"만 봤다. 시행문형은 이름이 직위 **오른쪽 같은 줄**에 온다.
     → 영역별 짝짓기 창(PAIR_WINDOW)으로 분리. 텍스트 레이어 이름 54.7 → 73.8%.
  2. 접힌 직위 병합 한계 16pt vs 격자형 머리행 간격 18pt — 2pt 차이로 병합 실패.
     → 26pt 로 확대.
  3. 같은 열 판정을 중심 x 하나로 했는데, 시행문형은 왼쪽 정렬·격자형은 가운데 정렬이라
     한쪽을 맞추면 다른 쪽이 깨졌다. → 두 기준 중 하나라도 맞으면 같은 열로 본다.
     (왼쪽만 쓰니 92.7→82.7 로 후퇴, 중심만 쓰니 격자형이 깨짐 — 둘 다 필요했다)
  4. 결재란 영역을 비율로만 잘라 발신명의("경기도서관장")가 들어와 가짜 칸이 생겼다.
     → 결재 줄 위 **회색 구분 띠**를 도형에서 찾아 그 아래부터 "시행" 줄 직전까지로 좁혔다.
  5. PaddleOCR 이름 일치율이 정확히 0.0% 로 나왔다. 직위는 65.7% 인데 이름만 전멸 —
     좌표에 의존하는 쪽만 죽었다는 신호였다.
     원인: PNG 크기를 pymupdf 로 쟀는데 pymupdf 는 이미지를 **72dpi 포인트**로 돌려준다
     (595x80). 실제는 1653x223 픽셀이라 좌표가 2.78배 틀어졌다.
     → PIL 로 픽셀 크기를 재도록 수정. 이름 0.0 → 66.8%.

    Apple Vision     69.8%   51.0%   80.0%   4/10     1.8s

  묶어 칸별 좌표가 뭉개진다. PaddleOCR 은 줄 단위로 따로 검출해 칸 구조가 남는다.
  문자 인식만 보면 Vision 도 직위·이름을 정확히 읽는다. 대신 PaddleOCR 은 20배 느리고
  모델 다운로드가 필요하다.

  결론: 결재선 추출도 **텍스트 레이어가 1순위**(가장 정확하고 400배 빠름).
  OCR 은 스캔본과, 텍스트 레이어로도 안 풀리는 이름 칸(26%)을 메우는 보조 경로.
