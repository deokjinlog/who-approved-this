# 직무별 특화과제 계획서 — 전자결재 AI 리허설 (공공데이터 기반)

작성일: 2026-09-08 / 작성자: 최덕진 (AI/백엔드)
연계 프로젝트: SK에코플랜트 전자결재 재구축 — AI 기능 (품의서 초안 생성 · 결재라인 자동 삽입 · 첨부/메일 요약)

---

## 1. 과제 취지

회사 프로젝트의 AI 기능은 아직 요구사항이 컨셉 수준이고, 고객 데이터(과거 결재문서 700만 건, 전결규정, 조직정보)는 미팅 전까지 받을 수 없다. 그런데 기술적으로 먼저 답을 내둬야 하는 질문은 이미 정해져 있다.

- 이관 PDF에서 결재선·메타데이터를 얼마나 정확히 뽑을 수 있나
- 첨부에서 예산·업체·일정 같은 값을 구조화로 뽑을 수 있나
- 한국어 품의서 기준으로 어떤 임베딩·검색 구성이 나은가
- 한국어 OCR을 로컬로 돌리면 상용 DI 대비 어느 정도인가
- 한국어 장문 요약 품질을 무엇으로 재나

이 다섯 개는 전부 **공개된 공공 데이터로 리허설이 가능**하다. 공공 결재문서·공고·FAQ·관보·의안은 원문(PDF)과 정답(구조화 메타데이터/API)이 이미 쌍으로 존재하므로, 라벨링 없이 정확도를 숫자로 낼 수 있다. 고객 데이터가 오기 전에 방법론과 측정 파이프라인을 만들어 두고, 데이터가 오면 소스만 바꿔 끼우는 것이 이 과제의 목적이다.

## 2. 회사 프로젝트 요구사항 요약

(상세는 별도 문서 "SKEP 전자결재 AI 요구사항 파악" 참조)

### 2-1. 요구 기능 (고객 메일 기준)

| 기능 | 핵심 동작 | 필요 데이터 |
|---|---|---|
| ① 품의서 초안 자동 생성 | 기존 품의서 + 첨부 + 연결문서(기획품의→실행품의) 기반 RAG 생성, 또는 첨부+프롬프트만으로 생성. 초안 4~5개 보관 후 선택 삽입. 첨부는 하이브리드 OCR(VLM + MS DI) | 과거 품의서 본문, 첨부, 연결 관계 |
| ② 결재라인 자동 삽입 | 상단(기안/검토/승인)은 조직정보, 중간(예산·공시·계열사거래)은 품의 내용, 하단(협조)은 품의 내용+전결규정 | 조직정보, 전결규정, 과거 결재선 |
| ③ 첨부파일·메일 요약 | 개발범위 자료에 항목만 존재, 세부 미정 | — |

### 2-2. 데이터 전제
- 과거 결재문서 약 700만 건을 PDF로 이관, 제목·기안부서·기안자·결재선·일시 메타데이터 추출 필요
- ETL 기반은 Databricks(팀 안내), 1차 구축은 Azure Fabric + Cosmos DB
- 1차 검증 방식: 100건 골든셋 기반 정확도 90% 목표

## 3. 특화과제 설계

### 3-1. 공통 파이프라인

모든 트랙이 같은 구조를 쓴다. 한 번 만들면 나머지는 데이터 소스 어댑터만 교체.

```
[수집] 브라우저 에이전트 → 공공 포털에서 원문 PDF + 정답 메타데이터 수집
   ↓
[처리] M2 로컬 → 렌더링(200dpi) → 로컬 OCR / VLM / LLM 파싱
   ↓
[대조] 파싱 결과 vs 공개 정답 → 정확도·CER·일치율 산출
   ↓
[기록] 트랙별 결과표 + 실패 케이스 샘플 → 회사 프로젝트 의사결정 근거
```

원칙
- 정답을 만들지 않는다. 이미 두 형태로 존재하는 것만 고른다.
- 회사·고객 데이터는 절대 반입하지 않는다. 공개 데이터로만 수행.
- 상용 API 비용은 0에 가깝게. 로컬 처리 우선, 상용은 비교군으로 소량만.

### 3-2. 트랙별 정의

#### T1. 정보공개포털 원문 결재문서 — 결재선 추출 (핵심 트랙)
- 소스: open.go.kr 중앙부처·지자체 결재문서 원문 PDF + 제목·기안부서·기안자·결재일 메타데이터
- 처리: 로컬 VLM으로 결재란(기안/검토/결재/협조 칸) 인식 → 결재선 구조화
- 측정: 결재선 항목별 일치율, 메타데이터 4종 추출 정확도, 문서 양식별 편차

**T1a / T1b 분리 (2026-09-08, 10건 실측 후 확정)**

포털 메타데이터에 **결재선이 없다.** `결재정보` 컬럼은 10건 전부
`"(화면에 표시 항목 없음)"` 이고, 사람 이름은 `담당자`(기안자)까지만 나온다.
그래서 정답의 성격이 다른 두 갈래로 나눈다.

| | 대상 | 정답 | 지표 |
|---|---|---|---|
| **T1a** | 제목·생산기관·담당부서·담당자·생산일자·문서번호 6필드 | metadata.tsv | 필드별 일치율 |
| **T1b** | 결재선(기안/검토/결재/협조의 직위·이름) | **직접 만든** `DATA_ROOT/t1/approval_gold.tsv` | 역할별 직위/이름/칸수 일치 |

T1b 정답은 다른 데서 구할 수 없어 PDF 결재란을 눈으로 보고 만들었다(10건 56행).
리포 밖에 두고 커밋하지 않는다(실명 포함). 문서에 `기안/검토/결재` 라는 **역할 이름이
인쇄돼 있지 않아** 칸 위치로 추정했고, gold 의 `note` 에 "역할 추정"으로 표시했다.
사람이 못 읽는 칸은 `name` 을 `?` 로 두고 이름 채점에서 뺀다.

**결재란 양식은 두 가지였다** (SKEP 품의서와 비교할 재료)

| 양식 | 건수 | 위치 | 특징 |
|---|---|---|---|
| 시행문형 | 8 | 페이지 **하단**, 회색 띠 아래 | 직위 위 / 이름 아래로 가로 반복, `협조자` 줄 별도 |
| 내부결재 격자형 | 2 | 우측 **상단** 표 | 표 머리행이 직위, 아래 행이 이름 |

둘 다 `직위`와 `이름`만 인쇄되고 역할 라벨은 없다. 직위가 칸 폭을 넘으면 두 줄로
접힌다("출입국관리서/기", "온실가스종합정/보센터장"). 전결은 결재 칸에 `전결` 로 표시된다.
- 회사 환류: 700만 건 이관 시 메타데이터 추출 방식(텍스트 레이어 / OCR / VLM) 선택 근거. 결재라인 자동 삽입의 학습 데이터 형태 확정. 공공 품의서 문체 수천 건은 초안 생성 실험 코퍼스로 재사용
- 주의: 공공 결재 양식과 SKEP 품의서 양식(기안 후 협조/검토N 후 협조 구조)은 다르므로, 양식 종속 부분과 범용 부분을 분리해서 기록

#### T2. 나라장터 입찰공고 — 첨부 구조화 추출
- 소스: 조달청 공고문 PDF + 나라장터 OpenAPI 필드(예산·마감일·참가자격·낙찰방법)
- 처리: PDF → 로컬 LLM/VLM 구조화 추출 → JSON
- 측정: 필드별 정확도(정확 일치 / 정규화 후 일치)
- 회사 환류: 초안 생성 시 첨부에서 예산·업체·일정을 뽑는 단계의 방식과 기대 정확도. 초안 생성 지표(D16) 설계 참고

#### T3. 정부24·부처 FAQ — 수집형 RAG 골든셋
- 소스: 정부·공공기관 FAQ (질문 + 공식 답변 + 근거 법령/문서 링크)
- 처리: 질문-정답문서 쌍 수백 개 수집 → 임베딩 / 하이브리드(BM25+벡터) / reranker 조합 비교
- 측정: Recall@k, MRR
- 회사 환류: 한국어 기준 임베딩·검색 구성 결정(E21). 골든셋을 "제작"이 아니라 "수집"으로 얻는 프로세스 자체가 D17 답안
- 연계: 기완료한 "임베딩 모델 비교 조사"의 후보를 그대로 실험군으로 사용

#### T4. 관보·법령 — 한국어 OCR 정량 벤치마크 (워밍업)
- 소스: 관보 PDF + 국가법령정보 API 구조화 텍스트
- 처리: 200dpi 렌더링 → 로컬 OCR/VLM → 텍스트
- 측정: CER, WER, 표·번호 구조 보존율
- 회사 환류: 하이브리드 OCR 구성에서 로컬 모델이 MS DI를 어느 범위까지 대체 가능한지. 기완료한 "OCR·VLM 모델 비교 조사"에서 확인된 공백("한국어 순수 OCR 제3자 정량 벤치마크 없음")을 직접 채움
- 착수가 가장 빠름 (API 문서화 양호), 하루 안에 첫 숫자

#### T5. 국회 의안 원문 ↔ 전문위원 검토보고서 — 요약 벤치마크
- 소스: 의안정보시스템 법안 원문 + 전문위원 검토보고서
- 처리: 로컬 LLM 요약 → 검토보고서와 비교
- 측정: ROUGE + LLM-as-judge(사실 누락·왜곡 항목 체크)
- 회사 환류: 기능 ③ 첨부·메일 요약의 평가 방법과 로컬/상용 품질 격차

## 6. 리스크와 제약

- **양식 차이**: 공공 문서와 SKEP 품의서는 양식·용어가 다르다. 정확도 숫자는 "이 방법이 이 정도 나온다"의 상한선이 아니라 방법 선택 근거로만 쓴다.
- **개인정보**: 공공 결재문서에 기안자 실명이 있다. 수집 데이터는 로컬에만 두고, 결과표에는 이름을 싣지 않는다. 공공누리 이용조건 확인.
- **수집 부하**: 포털별 이용약관과 요청 간격 준수. 대량 수집보다 양식별 대표 샘플 위주.
- **로컬 자원**: M2 로컬 처리 기준으로 모델 크기 제한. 상용 모델은 비교군으로 소량만.
- **시간**: 개인 시간으로 수행. 트랙당 "첫 숫자"가 나오면 일단 닫고, 심화는 회사 프로젝트 필요가 생길 때.

## 7. 회사 프로젝트로의 연결

```
리허설 결과            →  요구사항 미확정 항목  →  미팅에서 낼 의견
T4 OCR CER            →  B5, C15              →  "이관 PDF는 텍스트 레이어 우선, 스캔본만 OCR"
T1 결재선 일치율       →  B4, B8, D16          →  "결재선은 VLM 추출 후 규칙 보정, 목표 지표는 항목 일치율"
T1b OCR 3종 비교       →  B5, C15              →  "스캔본 경로는 PaddleOCR 후보. 단 480배 느림"
T1c 결재선 예측        →  B4, B7, B8           →  "조직 코드 필수. 직위는 규칙·이름은 LLM"
T1b/T1c 전결·대결      →  B6                   →  "전결규정 없이는 최종 결재 칸을 못 정한다"
T1d 초안 생성          →  요구사항 ①           →  "첨부 OCR·연결문서 없이는 값이 빈다"
T1d 인명 마스킹        →  D19                  →  "참고 문서 실명이 초안에 복사된다. 컨텍스트 마스킹 필요"
T3 Recall@k           →  E21, D17             →  "임베딩은 X, 하이브리드 필수, 골든셋은 수집으로"
T2 필드 정확도         →  ① 첨부 추출          →  "예산·일정 추출은 구조화 프롬프트로 N% 가능"
T5 요약 평가          →  A2                   →  "요약 범위는 첨부 우선, 평가는 항목 체크 방식"
```

요구사항 파악에서 나온 질문 22개 중 기술적으로 답할 수 있는 것은 리허설로 먼저 답하고, 고객만 답할 수 있는 것(범위·데이터 제공 형태·전결규정)은 미팅으로 닫는다.

---

## 8. 후속

- T1 코퍼스 + 메타데이터 위에 LLM 위키(부서·사업·품의유형 단위 페이지, 문서 유입 시 갱신). 요약 기능 범위 확정 후 별도 리포.

### 부록 2. 2026-09-09 실측 요약 (미팅용 5줄)

측정으로 확인된 것만 적는다. 추정은 추정이라고 적는다.

1. **포털 메타데이터 부서명 ≠ 실제 조직.** (B7) 법무부 "총무과" 8건이 실제로는 **6개 기관**
   (안양교도소 2 · 대구합동청사 2 · 서울출입국청 · 인천공항출입국청 · 광주청사 · 대전청사).
   `생산기관`·`담당부서`·기관코드가 8건 모두 동일하고 실제 구분은 **문서 하단 주소에만** 있다.
   → 결재선 추천에는 **소속기관 단위 조직 코드가 필수**.

2. **이력 기반 결재선 추천은 조직당 과거 문서 5~7건이 있어야 동작한다.** (B4, B8)
   같은 케이스 집합에서 참고 1건 61.3% / 3건 61.3% / **7건 81.0%**(직위).
   1~3건에서는 다수결이 "최근 문서 복사"와 **수치까지 같다**.

3. **20건 기준 PaddleOCR 이 텍스트 레이어와 이름 추출 동률**(70.2% vs 70.3%), 480배 느림.
   ※ 단 **우리 표본에 스캔본이 없다.** 측정은 디지털 PDF를 200dpi로 렌더링한 이미지에서
   한 것이므로, "스캔본 경로 채택"은 **스캔 표본으로 재확인이 필요한 추정**이다.

4. **지출 문서 본문은 사실상 수치다.** (요구사항 ①) 지급액·산출내역·기간·지급대상·예산과목이 모두
   첨부에서 온다. 초안은 값을 `(   )` 로 비웠다(11/24). 구조는 맞고 값만 없다
   → **첨부 OCR 이 요구사항 ①의 전제**다.

5. **문서 간 인용이 실재한다.** (요구사항 ①) 20건 중 **8건**이 다른 문서를 문서번호로 인용한다
   (알림·지출·계획 등. "결과보고만"이 아니다). 인용된 **10개 문서가 전부 수집 범위 밖**이라
   20건 표본에서는 링크가 하나도 안 걸린다. 문서번호 파싱으로 링크 자동 생성은 가능하지만
   **선행 문서까지 함께 수집**해야 실제로 연결된다.

6. **참고 문서의 실명이 초안에 복사된다.** (D19) 조치 전 24개 초안 중 14개(58%)에
   gold 실명이 그대로 들어갔다. 생성 컨텍스트에서 인명을 마스킹하니 1/8(13%)로 떨어졌다.
   → 초안 생성 파이프라인에 **인명 마스킹이 기본값**이어야 한다.

7. **전결·대결은 문서에서 읽을 수 없다.** (B6) 경기도서관 8건 중 7건이 관장 전결이고
   1건은 관장 전결 + 정책팀장 대결이라 관장 칸에 이름이 인쇄되지 않았다.
   제목·본문으로는 알 수 없어 **전결규정을 별도로 받아야** 최종 결재 칸이 정해진다.

## 부록. 2026-09-08 실측으로 갱신된 가설

**"이관 PDF는 텍스트 레이어 우선, 스캔본만 OCR" 은 결재란에도 그대로 유효하다.**

한때 "결재란은 이미지라 OCR 경로가 기본이어야 한다"고 적으려 했으나, 이는 **오진이었다.**
결재란을 페이지 **상단**에서만 찾다가 8/10 문서에서 못 찾은 것이고, 실제로는 대부분
문서의 결재란이 **하단 시행문 블록**에 있었다. 영역을 바로잡고 다시 재니 **10건 모두
결재란이 텍스트 레이어로 존재**했다.

실측 (10건, `results/t1/`)

| 경로 | 직위 일치 | 이름 일치 | 칸 수 일치 |
|---|---|---|---|
| 텍스트 레이어 | **92.7%** | 54.7% | 95.0% (9/10 문서 완전 일치) |
| Apple Vision OCR | 48.1% | 34.2% | 77.5% (2/10) |

따라서 결재선 추출도 **텍스트 레이어가 1순위**다. OCR·VLM은 텍스트 레이어가 없는
스캔본과, 텍스트 레이어로 안 풀리는 이름 칸(54.7%)을 메우는 보조 경로로 둔다.

주의: OCR 48.1%는 ocrmac 의 읽기 성능이 아니라 **하한**이다. ocrmac 은 직위·이름
문자열 자체는 정확히 읽었고(관측 확인), 점수를 깎은 건 칸 짝짓기 휴리스틱이
OCR 좌표에 덜 맞는 부분이다. VLM 비교 전에 이 부분을 먼저 손봐야 공정한 비교가 된다.
