# T4 — 관보 OCR 정확도 측정 방법

이 문서는 **어떻게 쟀는지**를 설명한다. 숫자 자체는 [`README.md`](../README.md)에,
실행 기록은 [`worklog.md`](worklog.md)에 있다.

한 줄 요약: **관보 PDF를 200dpi 이미지로 렌더링해 OCR로 다시 읽고, 그 PDF에 원래
들어 있던 텍스트 레이어와 글자 단위로 대조한다.** 사람이 정답을 만들지 않는다.

```
관보 PDF ─┬─ 텍스트 레이어 추출 (pymupdf)           → 정답
          └─ 200dpi PNG 렌더링 → OCR (Apple Vision) → 예측
                                    ↓
                          정규화 후 jiwer 로 CER/WER
```

---

## 1. 지표 정의

구현: `src/who_approved_this/evaluate/text_cer.py` · `TextCEREvaluator.evaluate()`

### CER (Character Error Rate, 글자 오류율)

`jiwer.cer(ref, hyp)` 를 그대로 쓴다.

```
CER = (치환 + 삭제 + 삽입) / 정답 글자 수
```

정답과 예측을 **글자 단위 편집 거리**(Levenshtein)로 맞춰 최소 편집 횟수를 세고,
정답 글자 수로 나눈다. 0이면 완벽, 1이면 정답 길이만큼 고쳐야 한다는 뜻이다.
**1을 넘을 수 있다** — 예측이 정답보다 훨씬 길어 삽입이 많으면 그렇다.

### WER (Word Error Rate, 어절 오류율)

`jiwer.wer(ref, hyp)`. 같은 계산을 **공백으로 자른 토큰** 단위로 한다.
한국어에서는 어절 단위가 되고, 띄어쓰기 하나만 달라져도 두 어절이 통째로 틀린 것으로
세기 때문에 **과대평가된다**. 참고 지표로만 본다.

### 무엇을 한 덩어리로 재나 — 세 층이 다르다

구현: `src/who_approved_this/tracks/t4_gazette_ocr.py`

| 값 | 계산 | 위치 |
|---|---|---|
| 페이지별 CER | 페이지 정답 ↔ 페이지 OCR 을 각각 대조 | `_run_document()` 안의 페이지 루프 |
| **문서 전체 CER** | 페이지들을 `"\n\n"` 로 이어 붙여 **한 번에** 대조 | `_run_document()` 의 `overall` |
| 유형별 CER | 그 유형 페이지들의 **페이지 CER 산술평균** | `_type_means()` |
| 요약 `cer_mean` | 문서들의 `overall.cer` 산술평균 | `run()` 의 `summary` |

**문서 전체 CER 은 페이지 평균이 아니다.** 전문을 이어 붙여 한 번 재므로 결과적으로
**글자 수 가중**(긴 페이지가 더 큰 영향)이 된다. 반대로 유형별 CER 은 페이지 산술평균이라
**짧은 페이지와 긴 페이지를 같게** 본다. 두 값이 다르게 나오는 이유가 이것이다.

### 함께 내는 보조 지표

| 이름 | 뜻 |
|---|---|
| `cer_raw` / `wer_raw` | 정규화를 **하지 않고** 원본끼리 잰 값 |
| `cer_no_leader` | 목차 점선 리더를 지우고 잰 값 |
| `cer_nospace` | 공백을 전부 빼고 잰 값 |
| `char_overlap` | 순서를 무시한 글자 겹침 (§4) |
| `ref_chars` / `hyp_chars` | 정규화 후 정답·예측 글자 수 |

## 2. 정답을 어떻게 뽑았나

구현: `src/who_approved_this/collect/local_files.py` · `TextLayerCollector._read()`

관보 PDF는 **텍스트 레이어가 살아 있는 네이티브 PDF**다. 즉 "이 페이지에 무슨 글자가
찍혀 있는지"를 PDF 자신이 알고 있다. 그걸 정답으로 쓴다.

```python
doc[i].get_text(sort=True)
```

### `sort=True` 가 핵심이다

pymupdf 의 기본값(`sort=False`)은 **PDF 안에 그려진 블록 순서**를 준다. 그건 사람이
읽는 순서와 다르다. OCR 은 화면에 보이는 순서로 읽으므로, 정답을 그리는 순서로 두면
**글자를 다 맞혀도 순서 차이가 CER 로 잡힌다.**

실측에서 이 한 줄이 **CER 0.2755 → 0.1105** 를 갈랐다. 20페이지 전부 개선됐다.

`sort=True` 는 블록을 위→아래, 왼→오른쪽으로 정렬한다. 즉 **정답과 예측이 같은 읽는
순서 규약을 쓰도록 맞춘 것**이지, "옳은 순서"를 별도로 정의한 게 아니다(§6 참조).

### 예측(OCR)은 어떻게 만드나

구현: `src/who_approved_this/parse/render.py` · `render_pdf()`,
`src/who_approved_this/parse/ocr_apple.py` · `AppleVisionOCRParser.parse_pages()`

1. `render_pdf()` — 페이지를 200dpi PNG 로. `DATA_ROOT/t4/rendered/<pdf명>/p{n}.png`
   에 저장하고 다음 실행 때 재사용한다. dpi 가 바뀌면 다시 그린다.
2. `ocr_image()` — Apple Vision(`ocrmac`)으로 읽고, 관측을 **위→아래, 왼→오른쪽**으로
   정렬해 줄바꿈으로 잇는다. Vision 좌표는 좌하단 원점 정규화 좌표라 y 를 뒤집어 정렬한다.

해상도는 결과에 영향이 없었다 — 200/300/400/600dpi 에서 CER 0.676 → 0.678 로 변하지 않았다.

## 3. 정규화 — "후"에 적용되는 단계

구현: `text_cer.py` · `normalize()`

```python
NFC 정규화 → 부호 통일(unify_punct) → (선택) 리더 제거(drop_leaders) → 공백 압축 → strip
```

**리더 제거는 기본값에 들어 있지 않다.** 지표를 유리하게 만드는 조작이 기본값에 숨지
않도록, 리더를 뺀 값은 `cer_no_leader` 로 따로 보고한다.
기본 정규화 문자열은 결과 JSON 의 `normalization` 필드에 그대로 실린다 —
`nfc + quotes + interpunct + whitespace-collapse`.

| 순서 | 단계 | 왜 필요했나 (실제 사례) |
|---|---|---|
| 1 | **NFC** (`unicodedata.normalize`) | macOS 는 한글을 자모 분리(NFD)로 저장하기도 한다. 글자는 같은데 코드포인트가 달라 CER 이 부풀려진다 |
| 2 | **따옴표 통일** | 정답은 둥근 따옴표 `“ ”`, OCR 은 곧은 따옴표 `"`. 20페이지에서 정답 쪽 137개 삭제 + 예측 쪽 105개 삽입으로 잡혔다 |
| 2 | **가운뎃점 통일** | 정답은 `ᆞ`(U+119E, 아래아)를 구분점으로 쓰는데 OCR 은 `•`(U+2022)로 읽는다. 치환 60건 + 삽입 68건 |
| 3 | **리더 제거** (옵션) | **목차 점선.** 21317호 1페이지는 정답 글자의 **64.3%가 `·`** 였다. 목차 줄이 `법률제21882호(국회법 일부개정법률) ·········· 4` 형태라 점이 본문보다 많다. OCR 은 점선을 재현하지 않아 CER 이 그대로 점선 비율을 따라갔다 |
| 4 | **공백 압축** (`\s+` → 한 칸) | 관보는 자간을 공백으로 벌려 찍는다(`대 통 령`, `관    보`). 본문 페이지 정답 글자의 **25~30%가 공백**이다 |

각 단계가 얼마나 기여했는지는 `cer_raw`(정규화 전)와 대조하면 보인다 —
21317호 20페이지에서 **0.4324(정규화 전) → 0.4169(정규화 후)**, 리더까지 빼면 **0.2277**.

## 4. 읽는 순서 문제와 `char_overlap`

### 2단 조판은 결국 문제가 아니었다

처음에 본문 CER 이 높은 원인을 **2단 조판**으로 의심했다. pymupdf 블록의 x 좌표가
`[50, 300]`(페이지 폭 595)으로 나와 두 단으로 보였기 때문이다.

**틀린 진단이었다.** 세로 여백 탐지 + 단 인식 정렬(XY-cut)을 구현해 돌렸더니 CER 이
**0.4367 → 0.4429 로 오히려 나빠졌고**, 실제 페이지를 열어보니 **1단**이었다.
x≈300 은 가운데 정렬된 제목·서명 줄이었다. 그 코드는 되돌렸다.

관보 3개 호 전체를 분류한 결과 `body_2col` 로 잡힌 페이지는 **0건**이다(§5).
읽는 순서 문제의 실제 원인은 **정답 쪽 블록 순서**였고, `get_text(sort=True)` 로 해결됐다(§2).

### `char_overlap` — 순서를 무시한 지표

구현: `text_cer.py` · `char_overlap()`

```
char_overlap = |정답 글자 다중집합 ∩ 예측 글자 다중집합| / |정답 글자 다중집합|
```

공백을 뺀 뒤 `collections.Counter` 의 교집합을 쓴다. **글자가 몇 번 나오는지까지 세지만
순서는 보지 않는다.** 1.0 이면 정답에 있는 글자를 개수까지 똑같이 뱉었다는 뜻이다.

### 두 값이 벌어지면 무슨 뜻인가

| CER | `char_overlap` | 해석 |
|---|---|---|
| 높음 | **높음** (0.9+) | **글자는 맞고 순서만 다르다.** 읽는 순서·레이아웃 문제 |
| 높음 | **낮음** (0.6 이하) | **글자를 아예 못 읽었다.** 인식 실패이거나 영역 누락 |
| 낮음 | 높음 | 정상 |

실측 예 — 본문 페이지는 겹침 0.98~0.99 인데 CER 0.16~0.49 였다. 순서 문제라는 신호였고
실제로 정답 쪽 정렬을 고쳐 해결됐다. 반대로 21317호 표 페이지 p228 은 겹침 **0.295** 로,
이건 순서가 아니라 **글자를 못 읽은 것**이다.

## 5. 페이지 유형 분류와 유형별 결과

구현: `src/who_approved_this/collect/page_type.py` · `classify_page()`

**규칙 4개, 위에서부터 처음 걸리는 것.** 정교한 레이아웃 분석이 아니라 결과를 묶어 보기
위한 거친 꼬리표다. 입력은 텍스트 레이어뿐(OCR 결과를 쓰지 않는다).

| 순서 | 유형 | 조건 | 상수 |
|---|---|---|---|
| 1 | `toc` | 리더 문자(점 3개 이상 연속) 비율 ≥ 15% | `TOC_LEADER_RATIO = 0.15` |
| 2 | `table` | 줄 수 ≥ 10 이고, 20자 미만 짧은 줄이 60% 이상 | `TABLE_MIN_LINES`, `SHORT_LINE_CHARS`, `TABLE_SHORT_RATIO` |
| 3 | `body_2col` | 페이지 가운데(30~70% 구간)에 글자가 전혀 없는 세로 띠가 폭 3% 이상 | `GUTTER_MIN_WIDTH`, `GUTTER_CENTER` · `has_gutter()` |
| 4 | `body_1col` | 나머지 | — |

### 유형별 CER (200dpi, Apple Vision, 유형을 섞어 20페이지씩)

| 유형 | 제21317호 (337p) | 제21316호 (440p) |
|---|---|---|
| `body_1col` 본문 | **CER 0.1193** / 겹침 0.984 | **CER 0.1528** / 겹침 0.994 |
| `table` 표·서식 | CER **0.3941** / 겹침 0.663 | CER 0.1460 / 겹침 0.968 |
| `toc` 목차 | CER 0.5829 → 리더 제외 **0.0832** / 겹침 0.397 | CER 0.6142 → 리더 제외 **0.0849** / 겹침 0.371 |
| **문서 전체** | CER 0.4169 / 리더 제외 0.2277 | CER 0.3493 / 리더 제외 0.1359 |

읽는 법 세 가지.

- **본문이 실제 성능이다.** CER 0.12~0.15, 겹침 0.98 이상.
- **목차는 리더가 전부다.** 리더를 빼면 0.08 로 본문보다 오히려 낫다.
- **표는 문서마다 갈린다.** 21316 은 0.146 인데 21317 은 0.394 이고 겹침이 0.66 까지
  떨어진다. 겹침이 낮다는 건 순서가 아니라 **글자를 못 읽었다**는 뜻이다(§4).
  로컬 OCR 이 무너지는 지점은 표다.

`body_2col` 은 3개 호 전체에서 **0건**이었다.

## 6. 이 측정이 못 재는 것

스캔본이 없다는 점 외에도 여러 개다. 숫자를 인용할 때 함께 말해야 한다.

**① 스캔본을 못 잰다.** 표본이 전부 텍스트 레이어가 살아 있는 **네이티브 PDF** 다.
측정은 그걸 200dpi 로 렌더링한 **깨끗한 이미지**에서 했다. 실제 스캔본에는 기울기·노이즈·
번짐이 있어 더 낮게 나올 가능성이 크다. **"스캔본에서도 이 정확도"는 근거 없는 주장이다.**

**② 표의 셀 구조를 못 잰다.** CER 은 문자열 하나를 비교하는 지표라 **행·열 경계, 셀
병합, 표 안의 읽는 순서**가 맞았는지 전혀 알 수 없다. 셀 내용이 뒤섞여도 글자만 같으면
CER 은 낮게 나온다. 표를 구조로 뽑는 일(HTML/마크다운 표)은 이 측정 밖이다.

**③ 서식을 못 잰다.** 굵기·글자 크기·들여쓰기·정렬·항목 번호 계층은 텍스트 레이어에서도
OCR 에서도 문자열로 평평해진다. "1. 가. 1)" 같은 계층이 유지됐는지 못 본다.

**④ 숫자 오류가 묻힌다.** 금액 `10,474,360` 에서 한 자리가 틀려도 CER 기여는 전체
글자 수 분의 1이다. 결재문서·지출 문서에서 **숫자 한 자리는 치명적**인데 이 지표는
그걸 다른 글자와 똑같이 센다. 숫자 정확도는 따로 재야 한다
(T5 의 `grounded_ratio` 가 그 방향이다).

**⑤ 정답이 정답이라는 보장이 없다.** 텍스트 레이어가 곧 원문이라는 가정 위에 있다.
텍스트 레이어 자체가 부정확한 PDF(스캔본에 얹힌 OCR 레이어 등)라면 **정답이 틀린 채로
점수가 나온다.** 관보는 정부가 만든 네이티브 PDF라 신뢰도가 높지만, 일반화할 수 없다.

**⑥ 읽는 순서는 "맞춘" 것이지 "잰" 것이 아니다.** 정답·예측 양쪽을 같은 규약
(위→아래, 왼→오른쪽)으로 정렬했다. 진짜 읽는 순서가 그것과 다른 레이아웃
(다단·박스·각주)에서는 두 쪽 다 틀린 채로 CER 이 낮게 나올 수 있다.

**⑦ 이미지·도장·서명은 대상이 아니다.** 텍스트 레이어에 없으므로 정답에도 없고,
OCR 이 무언가 읽어내면 오히려 삽입 오류로 잡힌다.

**⑧ 표본이 좁다.** 관보 3개 호, 특정 조판·서체다. 다른 기관 문서 양식에 그대로 옮길 수 없다.

## 7. 한 페이지 예시

### 정상 사례 — 제21317호 p11 (`body_1col`)

```
정답 원본   '제 21317호                 관      보                               2026-09-08\n\n 하지 아니하는 경우에도 '
OCR  원본   '제21317호\n관\n보\n2026-09-08\n하지 아니하는 경우에도 그 범죄수익등을 몰수할 수 있다.\n1. 범인이 사망한 경우\n'
정답 정규화 '제 21317호 관 보 2026-09-08 하지 아니하는 경우에도 그 범죄수익등을 몰수할 수 있다. 1. 범인이 사망한 경우 2. 범인이 국외도피소재불명, 등의 '
OCR  정규화 '제21317호 관 보 2026-09-08 하지 아니하는 경우에도 그 범죄수익등을 몰수할 수 있다. 1. 범인이 사망한 경우 2. 범인이 국외도피, 소재불명 등의 '

CER 0.0602   char_overlap 0.9951
```

남은 차이는 머리글 자간(`제 21317호` vs `제21317호`)과 **정답 쪽 쉼표 위치**다.
`국외도피소재불명,` 은 정답(텍스트 레이어)이고 `국외도피, 소재불명` 이 OCR 인데,
사람이 보면 **OCR 쪽이 맞다.** 텍스트 레이어의 쉼표가 다른 위치에 저장돼 있어서다.
§6-⑤ 의 실제 사례다 — 정답이 틀리면 OCR 이 맞아도 오류로 잡힌다.

### 리더 사례 — 제21317호 p1 (`toc`)

```
정답 정규화 '대한민국정부 제21317호 2026-09-08 【법 률】 ○ 법률제21882호(국회법 일부개정법률) ·································'
OCR  정규화 '대한민국정부 관©보 https://gwanbo.go.kr 제21317호 2026-09-08 [법 률】 · 법률제21882호(국회법 일부개정법률) 4 · 법률제21'

CER 0.6453   char_overlap 0.3343   (리더 제외 시 CER 0.1078)
```

세 가지가 한 번에 보인다.
정답에는 없는 **로고 글자**(`관©보`, `https://gwanbo.go.kr`)를 OCR 이 읽어 삽입 오류가 되고,
정답의 **점선 리더**를 OCR 은 재현하지 않아 삭제 오류가 되며,
글머리표 `○` 를 `·` 로 잘못 읽는다(20페이지에서 96건). 겹침이 0.33 인 이유다.
