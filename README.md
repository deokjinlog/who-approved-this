# who-approved-this

공개 공공데이터로 **문서 파싱 정확도를 숫자로 재는** 벤치마크 파이프라인.
이름 그대로 최종 목표는 "결재문서를 던지면 누가 결재했는지 뽑는다"(T1).

전자결재 AI 과제(결재문서 PDF에서 결재선·메타데이터 추출) 리허설용으로,
고객 데이터 없이 공개 데이터로 방법을 먼저 검증한다. 전체 계획은 [`docs/plan.md`](docs/plan.md),
진행 기록은 [`docs/worklog.md`](docs/worklog.md).

## 왜 CER인가

**CER(Character Error Rate, 글자 오류율)** = (틀린 글자 + 빠진 글자 + 끼어든 글자) ÷ 정답 전체 글자 수.
0이면 완벽, 0.05면 100자 중 5자꼴로 틀린 것.

단어 단위(WER)를 쓰지 않는 이유는 **한국어는 띄어쓰기가 흔들리면 단어 경계가 달라지기 때문**이다.
"결재 라인"과 "결재라인"은 사람 눈에 같지만 WER은 두 단어 모두 틀린 것으로 센다.
그래서 한국어 OCR 평가는 CER이 표준이고, WER은 참고 지표로만 함께 뽑는다.

**이 숫자로 무엇을 정하는가.** OCR·VLM 후보 여러 개를 같은 관보 페이지에 돌려
CER을 나란히 놓으면 "어느 모델이 한국어 공문서를 제일 정확히 읽나"가 숫자로 갈린다.
남의 벤치마크를 인용하는 대신 직접 낸 숫자라 근거로 쓸 수 있다.
실무로는 이관 대상 PDF를 **텍스트 레이어 그대로 쓸지 / OCR을 돌릴지 / VLM까지 쓸지**를
가르는 기준이 되고, 하이브리드 구성에서 로컬 모델이 상용 Document Intelligence를
어디까지 대체하는지도 여기서 나온다.

**정답이 무엇인지가 곧 구도다.** 지금 T4의 정답은 관보 PDF의 **텍스트 레이어**다.
원문이 무엇인지 정확히 아는 상태에서 OCR 성능만 떼어 보는 구도다.
텍스트 레이어가 없거나 깨진 스캔본은 이 방식으로 잴 수 없고, 그건 국가법령정보 API
텍스트를 정답으로 붙일 때 다룬다.

**CER은 T4 전용이다.** T1 결재문서는 글자를 얼마나 잘 읽었는지가 아니라
기안자·검토자·결재자를 **필드로 제대로 뽑았는지**를 보므로 항목별 일치율로 바뀐다.
둘 다 "정답이 이미 있으니 대조한다"는 구조는 같고 재는 단위만 다르다.

## 구조

공통 골격은 **collect → parse → evaluate** 3단계다. 트랙은 각 단계의 어댑터만 추가하고
골격(base 클래스 인터페이스, 패키지 구조)은 바꾸지 않는다.

```
src/who_approved_this/
  config.py    DATA_ROOT / RESULTS_ROOT
  collect/     소스 어댑터.  base.Collector  → (pdf_path, ground_truth) yield
  parse/       렌더링·OCR·VLM. base.Parser    → pdf_path 받아 str | dict 반환
  evaluate/    대조.          base.Evaluator → (parsed, ground_truth) 받아 점수 dict 반환
  tracks/      트랙별 조합·실행
  cli.py       typer 앱 (`wat run <track>`) — 트랙은 TRACKS dict 에 한 줄 추가
results/       트랙별 점수 JSON (커밋 대상)
docs/          계획서·진행 로그
```

**데이터는 리포 밖에 둔다.** 기본 위치는 `~/data/who-approved-this`,
환경변수 `WAT_DATA_ROOT`로 덮어쓴다. 리포에는 PDF·원문·중간 산출물을 커밋하지 않고,
코드와 점수 JSON만 커밋한다. 결과 JSON·로그에는 기안자 등 **실명을 남기지 않는다**
(공공 결재문서에는 실명이 들어 있다).

## 실행

### 벤치마크 실행

```bash
uv sync
uv run wat run t4 --pages 3 --only 21317   # 관보 OCR
uv run wat run t1                          # 결재문서 필드·결재선
uv run wat run t1c                         # 결재선 예측
uv run wat run t1d                         # 품의서 초안
```

### 데모 서비스 (제품 아님)

두 기능을 눈으로 보는 로컬 데모. **인증 없음, localhost 전용.**

```bash
uv run wat serve      # http://127.0.0.1:8000/swagger
uv run wat ui         # http://127.0.0.1:7860
```

| 경로 | 하는 일 |
|---|---|
| `POST /approval-line/predict` | 조직·제목·본문 → 예측 결재선 + 참고한 문서 id |
| `POST /draft/generate` | 조직·제목 → 초안 n개 + 검색된 참고 문서 id·점수 |
| `GET /docs`, `GET /docs/{id}` | 문서 메타와 gold 결재선 유무 (**실명 제외**) |
| `GET /orgs` | 조직 목록 |

Gradio 화면은 탭 두 개다. **결재선** 탭은 왼쪽 gold / 오른쪽 예측을 칸 단위로 놓고
틀린 칸에 빨간 배경을 준다. **초안** 탭은 왼쪽 실제 문서 / 가운데 초안 3개 / 오른쪽
검색된 참고 문서를 보여준다. 고른 문서는 참고에서 제외한다(leave-one-out).

로컬 모델을 붙이면 규칙 기반 대신 LLM 이 답한다.

```bash
WAT_LLM_MODEL=qwen3:8b WAT_EMBED_MODEL=bge-m3 uv run wat ui
```

모델을 지정하지 않으면 결재선은 다수결 baseline, 초안은 **검색 결과만** 나온다.
API 는 계산을 새로 하지 않고 `tracks/` 코드를 그대로 호출한다
(`api/models` · `api/services` · `api/routers` 세 계층).

| 옵션 | 뜻 |
|---|---|
| `--pages N` | 문서당 앞에서부터 N페이지만 |
| `--docs N` | 훑을 문서 수 |
| `--only TEXT` | 파일명에 `TEXT`가 든 PDF만 (큰 문서를 실수로 돌리지 않으려고) |
| `--dpi N` | 렌더링 해상도 (기본 200) |

패키지 관리는 **uv**만 쓴다 (`uv add` / `uv run`). `pip` 직접 사용 금지.

## T4 — 관보 OCR

관보 PDF를 200dpi로 렌더링해 로컬 OCR로 다시 읽고, 원래 텍스트 레이어와 대조한다.
즉 **"텍스트 레이어 vs OCR"** 비교다.

```
~/data/who-approved-this/t4/
  제21317호_관보(정호)20260908.pdf   관보 원문
  README.txt                          출처·수집일 기록
  rendered/<pdf명>/p{n}.png           200dpi 중간 산출물 (자동 생성·재사용)
```

로컬 OCR은 **Apple Vision**(`ocrmac`)을 쓴다. 모델 다운로드가 없고 원문이 로컬 밖으로
나가지 않는다. 리눅스로 옮길 땐 `parse/`에 다른 `Parser` 구현체를 추가한다 — 골격은 건드리지 않는다.
상용 API는 비교군으로 소량만 쓴다.

### 현재 측정값 (200dpi, Apple Vision)

페이지는 **유형을 섞어** 골랐다(`--select mixed`). 앞 20장만 보면 목차·공포문에 치우쳐
문서를 대표하지 못한다. 전체 페이지를 유형으로 분류한 뒤 유형을 돌아가며 한 장씩 집는다.
어떻게 골랐는지는 결과 JSON의 `page_selection` 에 그대로 남는다.

| 문서 | 표본 | CER | 리더 제외 | 글자 겹침 |
|---|---|---|---|---|
| 제21317호 (337p) | 20p (toc 3 / body 9 / table 8) | 0.4158 | **0.2262** | 0.5945 |
| 제21316호 (440p) | 20p (toc 3 / body 9 / table 8) | 0.3485 | **0.1349** | 0.6932 |

**유형별로 갈라 보면 전혀 다른 그림이 나온다.**

| 유형 | 제21317호 CER (겹침) | 제21316호 CER (겹침) |
|---|---|---|
| `body_1col` 본문 | 0.1176 (0.986) | 0.1525 (0.994) |
| `table` 표·서식 | **0.3941 (0.663)** | 0.1460 (0.968) |
| `toc` 목차 | 0.5815 → 리더 제외 **0.0801** (0.399) | 0.6129 → 리더 제외 **0.0816** (0.372) |

* **본문은 CER 0.12~0.15, 글자 겹침 0.99.** 로컬 OCR이 안정적으로 읽는다.
* **목차는 리더가 전부다.** 리더를 빼면 0.08로 본문보다 오히려 낫다.
* **표는 문서마다 갈린다.** 21316은 0.146인데 21317은 0.394이고 겹침이 0.66까지 떨어진다.
  겹침이 낮다는 건 순서가 아니라 **글자를 아예 못 읽었다**는 뜻이다(21317 p228은 겹침 0.295).
  로컬 OCR이 무너지는 지점이 표라는 건, 이관 PDF 처리에서 표·서식 첨부를 따로 다뤄야 한다는 신호다.

#### 지표 읽는 법

| 지표 | 뜻 |
|---|---|
| `cer` | 기본 정규화(NFC + 따옴표·가운뎃점 통일 + 공백 압축). **리더를 지우지 않는다** |
| `cer_no_leader` | 목차 점선 리더(점 3개 이상 연속)를 지우고 잰 값 |
| `cer_nospace` | 공백까지 뺀 값. 관보는 자간을 공백으로 벌린다("대 통 령") |
| `char_overlap` | **순서 무관** 글자 다중집합 겹침. 1에 가까운데 CER이 높으면 순서만 다른 것 |
| `wer` | 어절 단위. 띄어쓰기에 과민해 참고로만 |

리더 제거를 기본 정규화에 넣지 않은 건 의도적이다. 지표를 유리하게 만드는 조작이
기본값에 숨으면 모델 비교의 근거가 사라진다. 지운 값은 별도 열로만 보고한다.

#### "0.4367은 OCR 정확도가 아니다" — 그 뒤

첫 측정값은 CER 0.4367이었고, 그 대부분은 OCR 품질이 아니라 **측정 아티팩트**였다.

| 원인 | 조치 | 효과 |
|---|---|---|
| 정답을 pymupdf **블록 순서**로 읽어 시각적 순서와 어긋남 | `get_text(sort=True)` | 0.2755 → **0.1105** |
| 둥근 따옴표 `“ ”` vs 곧은 따옴표 `"` | 따옴표 통일 | — |
| 가운뎃점 `ᆞ`(U+119E) vs `•`(U+2022) | 가운뎃점 변종 통일 | — |
| 목차 점선 리더(정답 글자의 48~64%가 점) | 기본값에서 빼고 `cer_no_leader` 로 분리 | 목차 0.61 → **0.085** |
| 자간을 공백으로 벌린 조판 | `cer_nospace` 병기 | — |
| 목차 한 장이 평균을 끌고 감 | 페이지 유형 태그 + 유형별 평균 | 본문 **0.12~0.15** 로 분리 |

원인이 아니었던 것도 기록해 둔다. **해상도**는 무관하다(200/300/400/600dpi에서 CER 무변화).
**2단 조판**도 아니었다 — 두 문서 337p·440p 전체를 분류한 결과 `body_2col` 은 0건이었고,
단 인식 정렬을 넣었더니 오히려 나빠져(0.4367 → 0.4429) 되돌렸다.

목차 글머리표 `○` 를 `·` 로 읽는 오인식(96건)은 **진짜 OCR 오류라 정규화하지 않았다.**

#### 읽는 방법

이 CER은 "Apple Vision의 절대 한국어 정확도"가 아니라
**"텍스트 레이어가 살아 있는 관보 PDF를 200dpi로 다시 읽었을 때의 재현율"** 이다.
같은 페이지·같은 정규화로 다른 OCR·VLM을 돌려 **나란히 비교할 때** 의미가 생긴다.
정규화 방식은 결과 JSON의 `normalization` 필드에 기록되므로, 비교 대상끼리 이 값이 같아야 한다.


## T1 — 결재문서 필드·결재선 추출

T4가 "글자를 얼마나 잘 읽나"였다면 T1은 **"필드를 제대로 뽑았나"** 다. 재는 단위가 다르다.

포털 메타데이터에 **결재선이 없어서**(`결재정보` 컬럼이 10건 전부
"(화면에 표시 항목 없음)") 트랙을 둘로 나눴다.

| | 대상 | 정답 | 지표 |
|---|---|---|---|
| **T1a** | 제목·생산기관·담당부서·담당자·생산일자·문서번호 | `metadata.tsv` | 필드별 일치율 |
| **T1b** | 결재선(기안/검토/결재/협조의 직위·이름) | 직접 만든 `approval_gold.tsv` | 역할별 직위/이름/칸수 |

T1b 정답은 다른 데서 구할 수 없어 PDF 결재란을 눈으로 보고 만들었다(10문서 56행).
리포 밖에 두고 커밋하지 않는다(실명 포함). 문서에 `기안/검토/결재` 라는 **역할 이름이
인쇄돼 있지 않아** 칸 위치로 추정했고, 사람이 못 읽는 칸은 `?` 로 두어 이름 채점에서 뺀다
("사람도 못 읽는 건 모델도 못 읽는다"는 기준선).

### T1b 결과 — 20건, 같은 gold, 같은 짝짓기 규칙

괄호는 10건일 때 값.

| 경로 | 직위 일치 | 이름 일치 | 칸 수 일치 | 칸수 완전일치 | 소요 |
|---|---|---|---|---|---|
| 텍스트 레이어 (pymupdf) | **94.3%** (92.7) | **70.3%** (73.8) | **97.5%** (95.0) | 19/20 (9/10) | 0.16s |
| PaddleOCR (PP-OCRv5 korean) | 90.8% (85.7) | 70.2% (66.8) | 96.2% (92.5) | 18/20 (8/10) | 76.3s |
| Apple Vision (ocrmac) | 72.4% (69.8) | 53.0% (51.0) | 87.5% (80.0) | 12/20 (4/10) | 3.5s |

표본이 두 배가 되자 **PaddleOCR이 이름에서 텍스트 레이어와 사실상 동률**이 됐다
(70.2 vs 70.3). 직위도 3.5%p 차이까지 좁혀졌다. 다만 480배 느리다.

**읽는 법.** 텍스트 레이어가 1순위다 — 가장 정확하고 400배 빠르다. OCR은 텍스트
레이어가 없는 스캔본과, 텍스트 레이어로도 안 풀리는 이름 칸(26%)을 메우는 보조 경로다.

**두 OCR이 갈린 이유는 인식이 아니라 구조다.** Apple Vision은 표의 여러 칸을 한
관측으로 묶는다(`'환경연구 환경연구 생물소재 생물자원'` = 칸 4개). 칸별 x 좌표가
뭉개져 직위–이름 짝짓기가 깨진다. PaddleOCR은 줄(칸) 단위로 따로 검출해 칸 구조가
남는다. 문자 인식만 보면 Vision도 `교위`·`청장`·이름을 정확히 읽는다.
대신 PaddleOCR은 모델을 내려받아야 하고(최초 1회) 20배 느리다.

### T1a 결과 (규칙 기반 텍스트 레이어, 문서 평균 46.7%)

```
20건: 제목 75% | 담당부서 75% | 담당자 65% | 생산일자 50% | 문서번호 60% | 생산기관 0%   (평균 54.2%)
10건: 제목 80% | 담당부서 80% | 담당자 70% | 생산일자 50% | 문서번호 70% | 생산기관 0%   (평균 58.3%)
```

20건에서 전반적으로 내려갔다. 2차 수집분에 양식 변형(격자형 내부결재, 문서번호 표기
차이)이 더 들어와서다 — 규칙 기반 추출이 양식에 얼마나 민감한지를 보여주는 값이다.

`담당자`는 T1b 결재란 **첫 칸(기안)** 에서 끌어온다 — 포털 정의상 담당자가 기안자이므로
별도 규칙을 두지 않았다(0% → 70%).

`생산기관`이 0%인 건 규칙 문제가 아니다. **10건 중 3건은 생산기관 값이 PDF 본문에
아예 없다**(포털이 붙인 메타데이터일 뿐). 나머지 7건도 발신명의가 자간을 벌린
형태(`법 무 부 장 관`)라 기관명만 떼어내기 어렵다. 규칙 추출 상한이 70%이므로
여기에 규칙을 더 쌓지 않고 남겨 둔다.

### 결재란 양식 (SKEP 품의서와 비교할 재료)

| 양식 | 건수 | 위치 | 특징 |
|---|---|---|---|
| 시행문형 | 8 | 페이지 **하단**, 회색 구분 띠 아래 | 직위 왼쪽 / 이름 오른쪽 같은 줄, `협조자` 줄 별도 |
| 내부결재 격자형 | 2 | 우측 **상단** 표 | 머리행이 직위(가운데 정렬), 아래 행이 이름 |

둘 다 역할 라벨 없이 직위·이름만 인쇄된다. 직위가 칸 폭을 넘으면 두 줄로 접히고
(`출입국관리서`/`기`), 정렬이 양식마다 달라 접힌 직위를 이을 때 왼쪽·가운데 두 기준을
모두 봐야 한다. 전결은 결재 칸에 `전결` 로 표시된다.


## T1c — 결재선 예측 (leave-one-out)

T1b가 "문서에서 결재선을 **읽어내기**"였다면, T1c는 **"아직 없는 결재선을 제안하기"** 다.
회사 기능 ②(결재라인 자동 삽입)의 리허설이다.

같은 부서 문서가 셋씩 있는 두 묶음에서 한 건을 빼고, 나머지 2건의 (제목·본문·결재선)과
대상 문서의 (제목·본문)으로 대상 결재선을 예측한다. 정답은 T1b와 같은 `approval_gold.tsv`.

```bash
uv run wat run t1c                      # baseline 둘만
uv run wat run t1c --model qwen2.5:7b   # ollama 모델까지
```

| 예측기 | 방식 |
|---|---|
| `baseline_copy` | 같은 부서 직전 문서 결재선을 그대로 복사 |
| `baseline_vote` | 칸 위치별 다수결(동률이면 최근 것) |
| `llm_local` | ollama 로컬 모델에 참고 2건 + 대상을 주고 JSON 요청 |

### 그룹은 부서명이 아니라 **실제 조직**으로

포털의 `담당부서` 로 묶으면 법무부 "총무과" 8건이 한 묶음이 되는데, 실제로는
**안양교도소·대구합동청사·서울출입국청 등 6개 조직**이 섞여 있다(직위 체계부터 다르다).
조직 키는 문서 하단 주소를 보고 gold 의 `org` 열에 적어 둔다.
조직당 1건뿐이면 참고할 과거 문서가 없어 예측 대상에서 뺀다.

| 조직 | 문서 | 케이스 |
|---|---|---|
| 경기도서관 | 8 | 8 |
| 안양교도소 | 2 | 2 |
| 대구합동청사 | 2 | 2 |
| (1건짜리 8개 조직) | 8 | 제외 |

### 베이스라인 결과 (12케이스)

| 예측기 | 직위만 | 이름 | 칸 수 | 직위 전부 맞음 | 케이스당 |
|---|---|---|---|---|---|
| baseline_copy | 53.1% | 28.2% | 83.3% | 0/12 | 0.0s |
| baseline_vote | 66.2% | 42.1% | 83.3% | 4/12 | 0.0s |
| llm_local (qwen3:8b) | 48.2% | 64.2% | 75.0% | 1/12 | 10.2s |
| **vote_titles+llm_names** | **66.2%** | **72.5%** | **83.3%** | **4/12** | 5.6s |

이름 66.9 → **72.5%** 는 ollama 호출을 `/api/generate` 에서 `/api/chat` 으로 바꾼 결과다.
generate 는 이어쓰기 엔드포인트라 프롬프트가 문서 모양이면 모델이 그걸 계속 이어 쓴다.

**규칙으로 뼈대, LLM 으로 내용** — 칸 구조·직위는 다수결이 만든 것을 쓰고 이름만 LLM 것으로
바꾸면 모든 지표에서 최고이고, **이름은 LLM 단독보다도 높다**(66.9% vs 64.2%).
다수결이 만든 칸 구조가 LLM 의 이름을 올바른 자리에 고정해 주기 때문이다.

**재표집 검증** — 참고 7건 중 5건을 무작위로 골라 5라운드 반복(예측기당 40회 측정).

| 예측기 | 직위 | 이름 |
|---|---|---|
| baseline_vote | 76.2% | 43.3% |
| llm_local | 65.9% | 84.0% |
| **vote_titles+llm_names** | **76.2%** | **84.0%** |

**결합이 이름에서 두 단독을 모두 이긴 라운드 5/5** — 한 번도 뒤집히지 않았다.
다만 같은 20건에서 참고 조합만 바꾼 것이라 **독립 표본이 아니다**.
확정하려면 조직당 5~7건씩 3~4개 조직이 필요하다(현재는 20건 중 8건이
같은 조직 문서가 하나뿐이라 예측에 쓰이지 못한다).

**LLM 은 직위에서 지고 이름에서 크게 이긴다.** 경기도서관만 보면 이름 80.0% vs 48.3%.
LLM 은 제목·본문을 읽고 **팀을 바꾼다** — 의원 요구자료(서무성) 문서에서 다수결이
`도서관운영팀장`(8건 중 5건)을 고를 때 LLM 만 `도서관정책팀장`으로 바꿔 완전 정답을 냈다.
반대로 이름은 맞히면서 직위 칸에 팀 이름을 적는 오류가 4건이다(직원 명부가 있으면 사라질 오차).
JSON 파싱 재시도 0회.

10건 시절 두 baseline 이 같은 점수였던 건 참고 문서가 2건뿐이라 다수결이 복사와
같아졌기 때문이다. 참고가 7건으로 늘자 vote 가 copy 를 13%p 앞선다.

| 조직 | copy 직위 | vote 직위 |
|---|---|---|
| 경기도서관 (참고 7건) | 61.3% | **81.0%** |
| 안양교도소 (참고 1건) | 46.7% | 46.7% |
| 대구합동청사 (참고 1건) | 26.7% | 26.7% |

### 과거 문서 몇 건이면 충분한가

경기도서관 8케이스만, 같은 케이스 집합으로 참고 문서 수만 바꿔 측정.

| 참고 문서 | 직위 | 이름 | 칸 수 |
|---|---|---|---|
| 1건 | 61.3% | 27.5% | 93.8% |
| 3건 | 61.3% | 27.5% | 93.8% |
| **7건** | **81.0%** | **48.3%** | 93.8% |

**1건과 3건이 완전히 같다.** 참고가 적으면 다수결이 "최근 문서 복사"로 무너진다.
7건에서야 실제 다수 패턴이 드러난다 → 이력 기반 결재선 추천은
**조직당 과거 문서 5~7건**이 있어야 작동한다.

### 산출물은 숫자가 아니라 이것

6케이스는 작다. 이 트랙의 결과물은 정확도가 아니라
**[`docs/t1c_missing_info.md`](docs/t1c_missing_info.md)** —
틀린 케이스마다 "무엇을 알았으면 맞혔을까"를 `조직정보 / 전결규정 / 문서유형규칙 / 표본한계`
로 분류한 문서다. 결재라인 자동 삽입에 어떤 입력이 필요한지를 공개 데이터로 먼저 확인한다.

프롬프트 템플릿은 값 없이 [`t1c_prompt.md`](src/who_approved_this/tracks/t1c_prompt.md)에
따로 둔다. 채워진 프롬프트(제목·본문·실명 포함)와 모델 출력은 저장하지 않는다.


### T1d 검색 세 방식 (경기도서관 8케이스, 제목만으로)

| 방식 | 같은 조직 top-3 | 같은 유형 top-3 | top-5 서로 다른 문서 |
|---|---|---|---|
| **`bm25`** | **2.38 / 3** | 75.0% | 4.62 |
| `vector` (bge-m3) | 2.00 / 3 | 75.0% | 4.62 |
| `hybrid` (RRF) | 2.25 / 3 | 75.0% | 4.38 |

**BM25 가 이겼다.** 제목에 조직명이 문자 그대로 들어 있어 어휘 매칭이 이미 강하고,
청크가 43개뿐이라 의미 검색이 이득을 낼 여지가 좁다. 세 방식의 **같은 유형 적중률이
75.0% 로 동일**한 게 핵심 — 유형을 가르는 건 검색 방식이 아니다.

### T1d 초안 생성 (qwen3:8b, 8케이스 × 3개 = 24개, 34분)

| 지표 | 값 |
|---|---|
| 항목 재현율 | 0.0% (지표 한계 — 아래) |
| 핵심어 재현율 | **56.2%** |
| 길이 비율 | 1.21배 |

항목 재현율 0%는 초안이 `지 출 액`, 실제가 `지 급 액` 처럼 한 글자씩 어긋나
앞 6글자 일치가 깨진 것이다. 구조가 없다는 뜻이 아니다.

**초안이 무엇을 지어내는지가 더 중요한 결과다.**

| 관찰 | 개수 |
|---|---|
| 다른 문서번호를 인용한 초안 | 15 / 24 |
| 인용된 번호 중 **지어낸 것** | **6 / 7** |
| 값을 `(   )` 로 비운 초안 | 11 / 24 |
| 다른 기관명이 섞인 초안 | 3 / 24 |
| gold 실명이 복사된 초안 | 14 / 24 |

**조치 후 재측정** — 생성 컨텍스트를 같은 조직으로 제한하고 참고 본문의 인명을
gold 명단으로 마스킹했다(초안은 케이스당 1개).

| | 조치 전 | 조치 후 |
|---|---|---|
| 다른 기관명 오염 | 3 / 24 | **0 / 8** |
| 실명 복사 | 14 / 24 | **1 / 8** |
| 허구 문서번호 | 6 / 7 | 4 / 6 |
| 핵심어 재현율 | 56.2% (3개 중 best) | **58.3%** (1개만으로) |

허구 문서번호만 안 줄었다 — **코드로 고칠 문제가 아니라 연결문서 데이터가 없어서**다.
초안 1개가 3개 중 best 를 넘은 건 **컨텍스트 품질이 생성 횟수보다 중요하다**는 뜻이다.

모델은 "앞 문서를 인용하며 시작한다"는 **형식은 정확히 학습했는데 어느 문서인지
알 방법이 없어 번호를 지어낸다.** 값은 지시대로 비웠다 — 구조는 맞고 값만 없다는 뜻이라,
첨부 추출을 붙이면 그 빈칸이 채워질 자리다.

자세한 분석은 [`docs/t1c_missing_info.md`](docs/t1c_missing_info.md) ·
[`docs/t1d_missing_info.md`](docs/t1d_missing_info.md).


## T5 — 관보 안건 요약 (RAG 가 관보에서도 되는가)

T1d 가 "같은 조직 결재문서로 초안을 쓴다"였다면, T5 는 **같은 파이프라인을 관보에
그대로 얹는다.** 문서 성격이 완전히 달라도(법령 개정문·고시·공고) 검색과 요약이
작동하는지, 어디서 갈리는지를 본다.

### 정답을 사람이 만들지 않아도 된다

관보 1~2페이지 **목차**가 그 호의 안건을 모두 나열하고, 각 항목에 **공식 제명과
시작 페이지**가 붙어 있다.

```
○ 법률제21884호(인사청문회법 일부개정법률) ·············· 6
○ 광주전파관리소고시제2026-11호(무선국(항공국) 호출명칭 변경) ····· 6
```

시작 페이지로 본문을 자르면 `(본문, 공식 제명)` 쌍이 자동으로 만들어진다.
T1 에서 gold 를 손으로 만들어야 했던 것과 대조적이다.
관보 3개 호에서 **안건 268건**이 나왔다.

| 종류 | 건수 |
|---|---|
| 고시 | 106 |
| 공고 | 103 |
| 법률 | 29 |
| 대통령령 | 23 |
| 부령·총리령·규칙 | 7 |

```bash
uv run wat run t5                                        # 검색만
uv run wat run t5 --model qwen3:8b --embed-model bge-m3   # 요약까지
```

### 검색 — 여기서는 벡터가 이긴다

제명으로 질의해 그 안건 본문이 상위에 오는가 (표본 24건).

| 방식 | top-1 | top-3 | 같은 종류 top-3 |
|---|---|---|---|
| bm25 | 75.0% | 91.7% | 100.0% |
| **vector** (bge-m3) | **79.2%** | 91.7% | 100.0% |
| **hybrid** (RRF) | **79.2%** | 91.7% | 100.0% |

**T1d 와 정반대다.** 거기서는 BM25 가 이겼는데(2.38 vs 2.00) 여기서는 벡터가 이긴다.
이유는 질의의 성격이다 — T1d 의 질의(결재문서 제목)에는 조직명이 **문자 그대로**
들어 있어 어휘 매칭이 강했다. 관보 제명은 `무선국(항공국) 호출명칭 변경` 처럼
본문과 어휘가 겹치지 않는 **개념 요약**이라 의미 검색이 필요하다.

→ **검색 방식은 코퍼스가 아니라 질의 성격이 정한다.** 한쪽에서 이겼다고
다른 트랙에 그대로 옮기면 안 된다.

### 요약 — 근거는 지키고, 제명은 절반쯤 맞힌다

| 지표 | 값 |
|---|---|
| 제명 재현율 | 61.8% |
| **숫자 근거율** | **99.2%** (21/22 토큰이 본문에 실재) |
| 압축률 | 7.1% |

**숫자 근거율 99.2% 가 이 트랙의 핵심 결과다.** T1d 초안에서는 모델이 문서번호를
**6/7 지어냈는데**, 여기서는 22개 숫자 토큰 중 21개가 본문에 실재한다.

차이는 과제 구조다. T1d 는 **없는 문서를 새로 쓰는 일**이라 근거가 없어 지어냈고,
T5 는 **주어진 본문을 줄이는 일**이라 지어낼 이유가 없다.
→ **RAG 요약은 안전하고, 문서 생성은 근거를 따로 공급해야 한다.**

종류별로는 갈린다.

| 종류 | 제명 재현율 | 숫자 근거율 |
|---|---|---|
| 총리령 (2) | 100.0% | 100.0% |
| 대통령령 (4) | 75.0% | 100.0% |
| 공고 (4) | 66.7% | 100.0% |
| 법률 (4) | 62.5% | 100.0% |
| 부령 (4) | 50.0% | 100.0% |
| **고시 (5)** | **40.0%** | 96.0% |

고시가 가장 낮다. 고시 제명은 `한국산업표준 개정 예고(KSBISO5053-1 등 1종)` 처럼
**본문에 안 나오는 분류어**를 쓰는 경우가 많아, 본문만 읽고는 그 표현을 복원할 수 없다.


### 질의응답형 RAG — 실제 사용 조건에서 재측정

제명으로 질의하는 건 실제 상황이 아니다. 사용자는 공식 제명을 모른 채 일상어로 묻는다.
그래서 안건마다 **제명 낱말을 쓰지 말라고 지시해** 자연어 질문을 만들고 다시 쟀다.
질문과 제명의 낱말 겹침은 **21.4%** — 어휘가 거의 겹치지 않는다.

| 방식 | top-1 | top-3 |
|---|---|---|
| bm25 | 79.2% | 91.7% |
| **vector** | **87.5%** | **95.8%** |
| hybrid | 83.3% | 95.8% |

| 답변 품질 | 값 |
|---|---|
| 정답 안건이 근거에 포함된 비율 | 95.8% |
| **답변 숫자 근거율** | **100.0%** (22/22) |
| 평균 답변 길이 | 96자 |
